# Payment transaction tracking: audit enrichment and self-service lookup page

Every payment lifecycle event is now recorded in `PaymentAuditLog` with a `TransactionStatus` column and `CustomerEmail` / `SessionId` attribution. A new `GET /api/payments/transactions?email=` endpoint returns all non-succeeded rows for a given address, and a standalone `/my-transactions` Angular page lets users look up their failed or pending attempts by email. The page is linked from the failed/cancelled states on `payment-success`, from a new card on `contact`, and from a header button on `daily-listings`.

Watch for: **unauthenticated email enumeration** on the transactions endpoint (confirmed) — any caller can query any email's transaction history. The `existingClaim` audit path omits `CustomerEmail` (confirmed) so those rows are permanently unattributed. The Angular component does not unsubscribe from the `queryParamMap` observable (likely subscription leak on SSR/navigation).

**Verdict**: CHANGES_REQUESTED

---

## High-level view

The three payment handlers now write an audit row on every code path — session creation, verification (six distinct outcomes), and webhook receipt. The migration adds all three columns and their indexes correctly.

The `GET /api/payments/transactions` endpoint is anonymous. The design doc acknowledges this trade-off, but the endpoint exposes error messages, amounts, action labels, and truncated payment IDs — not just a count. With no rate limiting an adversary can bulk-scrape any user's transaction metadata by email.

The `existingClaim` re-verification audit row is written without a `CustomerEmail` field. The row is unattributed and will never appear in any user's self-service results regardless of future filter changes.

The `/my-transactions` Angular component follows the project's standalone / OnPush / signals pattern. One structural gap: `ngOnInit` subscribes to `route.queryParamMap` and never unsubscribes, which leaks in SSR or on repeated navigation.

<details>
<summary>Issues (3)</summary>

1. **Unauthenticated email enumeration** — `GET /api/payments/transactions?email=` is publicly accessible with no auth, no rate limiting, and no CAPTCHA. An attacker can enumerate any email's transaction history (amounts, error messages, action labels). Add rate limiting (e.g., ASP.NET Core rate limiting middleware) before deploying to production.

2. **existingClaim path missing CustomerEmail** — The audit row written on the idempotency-check path (`existingClaim != null`) does not set `CustomerEmail`, leaving it null and permanently invisible to the self-service lookup. Populate `CustomerEmail` from `existingClaim.Listing?.OwnerEmail` or via a gateway call, or document the omission as intentional.

3. **queryParamMap subscription leak** — `ngOnInit` in `MyTransactionsComponent` subscribes to `this.route.queryParamMap` without storing the subscription or using `takeUntilDestroyed()`. In Angular SSR the subscription never completes and leaks on the server. Use `takeUntilDestroyed(inject(DestroyRef))` or `pipe(first())` if a single read is sufficient.

<summary>Details</summary>

### Audit coverage gaps in VerifyDodoPaymentCommandHandler

Six verification outcomes are covered. The unresolvable-paymentId path returns before any DB interaction — intentional since there's nothing to attribute. The idempotency path (`existingClaim != null`) writes a `Succeeded` row but leaves `CustomerEmail` null. The claim entity carries `PaymentAmount` and `ListingId` but getting an email here requires either including the `Listing` navigation property (already loaded via `Include(c => c.Listing)`) or a separate gateway call. The missing email means these rows are permanently orphaned from the user's audit trail.

### Unauthenticated transactions endpoint

The plan document explicitly acknowledges no auth is added at this stage. The endpoint exposes `ErrorMessage`, `Action`, `Amount`, `Currency`, and truncated payment IDs across up to 100 rows per query. With no rate limiting, an adversary with a list of emails can bulk-scrape transaction metadata. This should be treated as a known gap to close before going to production.

### Angular queryParamMap subscription leak

`ngOnInit` subscribes to `this.route.queryParamMap` without cleanup:

```typescript
this.route.queryParamMap.subscribe((params) => { ... });
```

In Angular SSR the Zone never completes so the subscription is never garbage-collected. In browser navigation, if the component is destroyed and recreated (e.g., navigating away and back), a new subscription accumulates. The fix is one line:

```typescript
this.route.queryParamMap
  .pipe(takeUntilDestroyed(this.destroyRef))
  .subscribe((params) => { ... });
```

where `destroyRef = inject(DestroyRef)` is declared alongside the other injected dependencies.

</details>
