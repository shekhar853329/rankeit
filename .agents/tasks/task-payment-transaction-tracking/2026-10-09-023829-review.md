# Payment transaction tracking: audit enrichment and self-service lookup page

Every payment lifecycle event is now recorded in `PaymentAuditLog` with a `TransactionStatus` column and `CustomerEmail` / `SessionId` attribution. A new `GET /api/payments/transactions?email=` endpoint returns all non-succeeded rows for a given address, and a standalone `/my-transactions` Angular page lets users look up their failed or pending attempts by email. The page is linked from the failed/cancelled/error states on `payment-success`, from a new card on `contact`, and from a header button on `daily-listings`. Both `dotnet build` and `ng build --configuration production` pass with zero errors.

Watch for: the three blocking concerns from the prior review pass (no rate limiting, missing `CustomerEmail` on the `existingClaim` path, `queryParamMap` subscription leak) are all confirmed fixed. No new blocking concerns found.

**Verdict**: APPROVED

## High-level view

All three payment handlers now write an audit row on every code path. `CreateDodoSessionCommandHandler` stamps `Pending`/`Failed` with `CustomerEmail` and `SessionId` at session creation. `VerifyDodoPaymentCommandHandler` covers six distinct outcomes including idempotency re-verification, with the `existingClaim` path now correctly sourcing `CustomerEmail` from the eagerly-loaded `Listing?.OwnerContactEmail`. `ProcessDodoWebhookCommandHandler` fixes the pre-existing bug where `webhookId` was stored as `PaymentId`, and adds `TransactionStatus` and `CustomerEmail` via a new `ExtractCustomerEmail` helper.

The transactions endpoint is publicly accessible by design — the plan doc acknowledges this trade-off explicitly. Rate limiting (fixed-window 10 req/IP/min) is in place to limit bulk scraping. The data exposed (amounts, error messages, truncated payment IDs) is meaningful but low-sensitivity for the user's own email.

The Angular `/my-transactions` component follows the project's standalone / OnPush / signals pattern precisely. The `queryParamMap` subscription is now cleaned up via `takeUntilDestroyed(this.destroyRef)`, closing the SSR leak from the previous iteration.

### Audit coverage across all three handlers

Six `VerifyDodoPaymentCommandHandler` outcomes each write an audit row: unresolvable-paymentId returns before any DB interaction (intentional — nothing to attribute); idempotency re-check (`existingClaim != null`) writes `Succeeded` with `CustomerEmail = existingClaim.Listing?.OwnerContactEmail`; payment-not-found writes `Unknown`; non-succeeded maps the raw gateway status via `MapPaymentStatus()`; metadata-missing writes `Succeeded` with `IsSuccess = false` (payment cleared, claim failed — accurately reflects the split outcome); succeeded+claim-placed and succeeded+claim-rejected both write `Succeeded` rows with different `IsSuccess` values.

`ProcessDodoWebhookCommandHandler` previously stored `command.WebhookId` in `PaymentId`. The fix stores `ExtractPaymentId(root)` instead, and `ExtractCustomerEmail(root)` traverses `data → customer → email` with null-safe property checks at each level.

### Rate limiting on the public endpoint

The `"transactions"` fixed-window limiter (10 requests/IP/minute, queue limit 0, 429 on rejection) is registered in `Program.cs` and `UseRateLimiter()` middleware is placed correctly after `UseCors()`. The controller action carries `[EnableRateLimiting("transactions")]`. This is a minimal but meaningful guard for a public, unauthenticated lookup endpoint.

### Angular component correctness

`MyTransactionsComponent` uses `@if`/`@for` control flow syntax consistently with the rest of the app — no `*ngIf` or `*ngFor` directives. The `ngOnInit` `queryParamMap` subscription is now piped through `takeUntilDestroyed(this.destroyRef)` before subscribing, which closes the SSR/navigation leak. The `statusClass()` helper handles `succeeded`/`success`, `pending`/`processing`, `failed`, `cancelled`/`canceled`, and `null` defensively, avoiding chip rendering failures if the backend ever returns an unexpected value.
